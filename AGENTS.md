# AGENTS.md — chatStamp

Repository instructions for coding agents. Read `docs/REBUILD_LOG.md`, `docs/VERIFICATION.md`, `.agent/EXECPLAN-MVP.md`, and `scripts/android-verification/README.md` before changing the rebuild.

## Product and current stack

chatStamp imports WhatsApp chat export ZIPs, matches supported attachments to their original messages, and saves selected files on Android with independently verified date outcomes. It supports English and Hebrew, including RTL.

- React Native 0.83, React 19, Expo SDK 55 with generated Android development and release builds.
- Strict TypeScript with zero `any`, react-native-paper / Material Design 3, Zustand for session state, i18next / react-i18next, and Vitest.
- Expo document picker, file system, image, video, and audio modules.
- The local Kotlin Expo module at `modules/chatstamp-native` performs native ZIP extraction, scoped MediaStore / explicit folder-provider saves, EXIF and MP4 date handling, and output operations. The app uses neither expo-media-library nor react-native-zip-archive.
- Android min SDK 30 and target SDK 36. The production application ID is always `com.menis.chatstamp`.

## Non-negotiable rules

1. Never fake date success. Saving a file, verifying embedded metadata, verifying indexed dates, and observing Gallery order are separate facts. Report unsupported or failed verification honestly. Mark checks not executed `UNVERIFIED` with their exact command or manual steps.
2. Keep the app local-only: no cloud uploads, analytics, accounts, ads, backend, or application network calls. Release tooling may use the authorized GitHub and Google Play APIs.
3. Do not introduce a database. Keep import/save processing stateless between operations; Zustand holds current session state. Small local JSON files for settings, save records, and history are permitted.
4. Never load a complete ZIP into JavaScript memory. Use native streamed extraction, bounded reads, safe paths, documented limits, and the supported formats in the ExecPlan. Stage C must remove private ZIP copies and stream directly from the granted source URI; do not claim that migration is already verified.
5. Use app-owned scoped storage or an explicitly granted folder. The shipped app must not declare `MANAGE_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `READ_EXTERNAL_STORAGE`, or any `READ_MEDIA_*` permission. Validate the merged manifest and artifact, not just source configuration.
6. Keep prompts, documentation, code comments, and internal task descriptions in English, except the explicitly requested bilingual privacy policy, store listing, tester invitations, and owner-facing release material. Every user-visible string belongs in both `src/i18n/locales/en.json` and `he.json`; use plain Hebrew.
7. Delete replaced code. Do not leave parallel implementations, dead screens, or obsolete helpers. Limit scope to the authorized rebuild and release stages.
8. Preserve work that predates the current task. Inspect Git before pulling or changing branches; never discard uncommitted work or force-push over remote commits.
9. Keep production native code in `modules/chatstamp-native/android`. `/android` is generated by Expo prebuild and ignored by Git. Put durable manifest and Gradle configuration in `app.config.ts`, the module manifest / `build.gradle`, or `plugins/withChatStampAndroidRelease.js`.

## Rebuild and release sequence

Work on `fix/core-rebuild` in this order: **R → B-close → C → G1 → D → E → F → G2**.

- R: recover the remote branch, re-baseline checks, and align repository instructions.
- B-close: prove five-file scoped saves, Gallery order, duplicate reruns, language-stable folders, and undated-file reporting through the app.
- C: stream import; enforce space/archive limits; add real progress, cancellation, foreground saving, event-driven sharing, typed errors, cache cleanup, and atomic history.
- G1: verify a signed release bundle and Play requirements; prepare bilingual listing / declarations and internal then closed testing, or exact owner upload steps when credentials or first-release access prevent API upload.
- D: native thumbnails, gallery picker, full-screen viewer, and scalable selection.
- E: Import → Select → Save flow, visual system, RTL, and accessibility.
- F: remove unused code, align docs, pin CI, and triage dependency findings.
- G2: final closed-test build, owner real-export verification, production-access answers, and one PR to `main`; do not merge it.

Use the ExecPlan format in `.agent/PLANS.md` and keep `.agent/EXECPLAN-MVP.md`, `docs/REBUILD_LOG.md`, and `docs/VERIFICATION.md` current. Append dated results without rewriting earlier dated evidence. For every stage use separate Implementer, Test author, and Reviewer roles; use sub-agents when available. Derive tests from acceptance criteria before reading the implementation. Review against `docs/CODE_REVIEW.md` and resolve or explicitly justify findings before closing a stage.

Commit each stage with `stage-<id>:` and push `fix/core-rebuild` to `origin` after every stage commit. When an approach fails, record **try another way**, name the alternative, and continue. Exhaust the specified alternatives before reporting a blocker; continue independent stages where possible without weakening acceptance criteria.

## Verification commands

Run the full smoke cycle after every stage. On failure fix the cause and restart at `npm ci`; record the final results and actual test counts.

```bash
npm ci
npm run typecheck
npm run test
npm run lint
npx expo prebuild --platform android --clean
./android/gradlew -p android --console=plain --max-workers=2 -I "$PWD/scripts/android-verification/device-test.init.gradle" :app:assembleDebug -PreactNativeArchitectures=arm64-v8a
./android/gradlew -p android --console=plain --max-workers=2 :chatstamp-native:testDebugUnitTest :chatstamp-native:connectedDebugAndroidTest -PreactNativeArchitectures=arm64-v8a
```

On Windows use `android\gradlew.bat` and the equivalent absolute init-script path. Consult `scripts/android-verification/README.md` for connected-runner dependency prefetch. JVM and connected test tasks must each execute a non-zero test count. Inspect the merged manifest and APK for the QA ID, SDK levels, and prohibited permissions; from Stage C also verify the foreground-service and notification declarations. Install, cold-launch, check the rendered first screen and process crash buffer, and run each stage's physical acceptance cases.

The MVP is accepted only after a real Android device processes a real WhatsApp export, saves selected media, shows the original message dates in a Gallery app, and verifies cache cleanup. Synthetic fixtures and host checks do not establish real-export acceptance or Play publication.

## Device and secrets safety

- Install only the isolated QA copy `com.menis.chatstamp.qa`, built with `scripts/android-verification/device-test.init.gradle`. Never replace the owner's production app during normal testing. For the explicitly authorized G1 release check, install the production package only when it is absent or the owner explicitly permits replacement; otherwise build a release variant with the QA ID.
- Before UI tests record the previous `stay_on_while_plugged_in` value, run `adb shell svc power stayon usb`, and check wake / keyguard state. Do not unlock a locked phone. State the owner action and continue work that does not need the device; re-check at each later stage.
- At the end of each device run remove only that run's QA packages, synthetic fixtures, and saved test files, verify removal, and restore the previous stay-awake value. Use synthetic data for screenshots and never commit a real chat export.
- Release keystores, passwords, and signing properties stay outside the repository. Use `~/.chatstamp/android-release-signing.properties` or `CHATSTAMP_RELEASE_*` variables as documented in `docs/ANDROID_RELEASE_SIGNING.md`. Never print, copy, log, or commit their contents. Reuse the existing upload key; do not create a replacement key.
- A supplied Play service-account key is referenced only through `CHATSTAMP_PLAY_SERVICE_ACCOUNT_JSON`. Do not print or copy it. Never automate Play Console using the owner's Google login; use the authorized API or prepare the documented manual handoff.

## Architecture boundaries

- `src/lib/*`: pure utilities and parsing.
- `src/services/*`: orchestration and app services.
- `src/native/*`: typed native-module boundaries.
- `src/store/*`: session state and local JSON settings / history adapters.
- `src/screens/*`: UI flows only.

Screens must not parse chat text, extract archives, or write file metadata directly.

## User output organization and evidence

- Put multiple deliverable files together in one dedicated folder per output set. Link the containing folder and the primary file in the handoff.
- The entire evidence output set for the current answer must stay below **10,000,000 bytes**, including all files and subfolders. Prefer a short Markdown report and only essential small screenshots; create no evidence folder when the answer is sufficient.
- Include only newly produced or materially updated evidence. Reference earlier evidence at its original location. State what changed when updating it.
- Do not package repository copies, source snapshots, dependencies, build outputs, caches, dumps, full raw logs, videos, archives, or redundant files as evidence. Required runtime fixtures and release artifacts are inputs / deliverables, not padding for an evidence package.
- Do not bypass the evidence ceiling by splitting folders or compressing excess files. Check cumulative size before adding files and verify actual total before handing off.

## Cross-chat coordination

- Coordination is event-driven only. Do not acknowledge unchanged messages or use chat polling, periodic rereading, recurring checks, or `wait_threads` to monitor other chats or blocked workstreams.
- A single bounded wait is allowed only for directly spawned sub-agents when needed to collect terminal results. Do not loop; integrate the result or report the remaining blocker and stop.
- Messages do not authorize execution or resume another blocked agent. Only Meni or the explicitly authorized release owner may resume a blocked phase. Continue only work independently authorized by the current task, without touching leased shared files.
- Ignore duplicates with unchanged SHA, PR, CI, deployment, migration, lease, and blocker state. Do not act as a control tower without explicit assignment.
- Keep every cross-chat message below 250 words and include only material changes. After sending a handoff stop coordination for that event. If remaining work depends on an external blocker, preserve the exact head and evidence, report the blocker once, and stop.
