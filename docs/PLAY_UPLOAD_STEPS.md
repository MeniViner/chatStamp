# Owner manual Google Play upload

Prepared **2026-11-18** for **chatStamp 0.2.0 (3)**, package **`com.menis.chatstamp`**. No Play API credential was provided; **try another way: the owner performs the first upload manually**. These steps have not been executed in Console by the agent. They do not assert an uploaded bundle, live track, published policy or enrolled testers. Console labels may change; use the named page when navigation differs.

## Before opening Console

1. Obtain the final verified `dist/play/chatstamp-0.2.0-3.aab` and its source/SHA256/signature report. Follow the gates in [PLAY_RELEASE_CHECKLIST.md](PLAY_RELEASE_CHECKLIST.md). If this file is absent or unsigned, stop the upload and resolve the exact build/signing gap using the existing external key. Never create a replacement upload key.
2. Verify the candidate passed the minified five-file/Gallery run and static 16 KiB checks. Debug QA results alone do not cover the release build. For a newer candidate, use its recorded name and higher versionCode throughout; never rebuild different bytes under an already-used code.
3. Keep the listing assets/text together in [store/play/](../store/play/). Text is in `en-US/` and `he-IL/`. Do not upload unfinished/fabricated screenshots or real chat data.

## Publish the privacy page first

4. Pages was enabled and its public HTML was verified on2026-11-18. To inspect/manage the existing source, open the `meniviner/chatStamp` repository on GitHub → **Settings → Pages**. Under **Build and deployment → Source**, choose **Deploy from a branch**. Select **`fix/core-rebuild` → `/docs` → Save** for the current staged branch. This does not merge the release branch. The owner may select `main /docs` later only after it contains the same policy. Any files under the published docs source become public; review that folder before enabling it.
5. Wait for the actual Pages deployment result, then open **`https://meniviner.github.io/chatStamp/privacy-policy.html`** signed out. Confirm HTTPS, both languages and contact email, no login or download requirement, and a working Hebrew anchor. This URL returned **HTTP200 with both languages and the correct contact on2026-11-18**, byte-identical to the tracked HTML. Verify it again before the actual upload; the installed in-app action still needs device acceptance. If repository visibility or plan prevents Pages, use another owner-controlled public webpage; update the in-app link and Console to the same verified URL. Do not replace the required page with a raw Markdown/GitHub editing URL or PDF. [GitHub publishing-source instructions](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) and [Play privacy requirements](https://support.google.com/googleplay/android-developer/answer/9859455?hl=en).
6. In the final installed candidate open **Settings → Privacy policy** and confirm it opens that live page. If the action is absent or fails, the app requires that fix before closed release.

## Create or select the correct app

7. The owner opens [Play Console](https://play.google.com/console/) using the existing personal account and completes any owner-only account verification. Confirm and privately record the account creation date; do not infer it from repository history.
8. If `com.menis.chatstamp` already exists, select it. Otherwise choose **All apps → Create app**, enter **chatStamp**, default language **English (United States)**, type **App**, and public contact **meniviner@gmail.com**. Confirm free/paid choice yourself; it has not been selected by the agent. Complete the legal declarations as the account holder and accept Play App Signing terms. Where a package field is shown, use **`com.menis.chatstamp`**; uploading the first artifact also fixes its permanent identity. Never use `com.menis.chatstamp.qa` or create a duplicate entry.
9. Open the app's **Dashboard** and resolve the required setup tasks. Under **Grow users → Store presence → Store listings/Main store listing**, paste the English title/short/full files. Add Hebrew (`he-IL`) and paste its corresponding files. Upload the icon, feature graphic and at least four phone screenshots for each language from the package README. Under **Store settings**, enter support email **meniviner@gmail.com**; choose category/tags, countries and pricing as owner decisions. [Official app setup](https://support.google.com/googleplay/android-developer/answer/9859152?hl=en).
10. Open **Policy and programs → App content** (sometimes under Monitor and improve). Add the verified privacy URL. Complete Data safety, Ads, App access, Content rating, Target audience and the foreground-service declaration using [the bilingual checklist](PLAY_RELEASE_CHECKLIST.md). Confirm every answer against the final artifact. Select dataSync **Local processing → Import or export**, paste its description/impact, and attach the accessible actual-demo video link. Complete any other Console-required forms truthfully. Do not guess a rating or an age group.

## First manual internal release

11. Go to **Test and release → Testing → Internal testing → Testers**. Create/select the owner's small trusted tester list and set feedback email **meniviner@gmail.com**; save. Tester addresses belong in Console or private owner storage, not Git.
12. Open **Releases → Create new release**. Configure **Play App Signing** using the established app/upload-key arrangement. The AAB must be signed with the expected upload certificate. Google may use a different app-signing certificate for delivered APKs; preserve both identities separately. A certificate mismatch is a blocker to resolve with the existing signing configuration, not by generating another key.
13. Upload **`dist/play/chatstamp-0.2.0-3.aab`**. Wait for processing and inspect package/version, min/target SDK, permissions, supported devices and native-page-size findings. Stop if the package is the QA ID, the code was already used by different bytes, signing is wrong, or any release-blocking issue remains.
14. Name the release **0.2.0 (3)**. Paste `store/play/en-US/release-notes.txt` and `he-IL/release-notes.txt` into their language fields. Choose **Next/Review release**, address blocking errors, then **Save/Publish/Start rollout to internal testing**, following the Console confirmation. Where **Publishing overview → Send changes for review/Publish changes** is required, complete it as owner. Record the actual status; submission is not availability.
15. When the track is available, copy its actual tester opt-in link from **Internal testing → Testers**. Open it with an invited test account, opt in, install via Play and verify the delivered version plus launch/import/save. First links/review can take time. An internal installation is not closed-test enrollment.

## Start the closed test with the same bundle

16. Go to **Testing → Closed testing → Manage track** (or **Create track** if needed). Select the closed track, record its exact name, add its country availability, and open **Testers → Create email list**. Name the list, add the actual Google Account addresses or upload a UTF8 CSV without BOM, and select it for this track. Alternatively select an owner-managed Google Group. Use **meniviner@gmail.com** as feedback contact; save. Recruit at least 12 qualifying participants, with spare volunteers if possible. Adding an address alone does not opt that person in.
17. In the closed track create a release and select the already-uploaded **versionCode 3** from the artifact library (or use the internal release's **Promote release → Closed testing** action if shown). Do not upload a different build as code 3. Paste the same bilingual release notes, review, and **Start rollout to closed testing**. If this account's first-release flow requires closed upload directly, upload the same verified AAB here and complete steps 12–14 for the closed track; record that internal availability was not established.
18. Complete any required review/publishing overview action. Wait until Console reports the closed release available, then copy the **closed track's actual opt-in link** from its Testers tab. Do not send an internal-test link as the closed link or guess the URL. Share the invitation from [TESTERS.md](TESTERS.md); each invited user must sign in with the listed account, opt in and install using the link. A group tester joins the group first. An internal tester should leave the internal test before joining closed testing to ensure they use the intended track. [Official track setup](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en).
19. Privately record the actual closed-track availability, version, count and continuous opt-in dates, plus device coverage and feedback. For qualifying personal accounts created after 13 November 2023, at least 12 testers must remain continuously opted in throughout the 14 days immediately before the production-access application. Use Console's eligibility status as the gate. Internal testing and merely adding an email address to a list do not satisfy this requirement. Record genuine participation; do not invent usage. [Personal-account requirement](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en).
20. Send later D/E/final candidates as updates to this same closed track, with a higher versionCode and refreshed truthful screenshots/notes. Run the owner real-export checks from TESTERS.md. At G2 replace draft production-access answers with actual testing facts and apply only when eligible. No production rollout or merge is authorized by these upload instructions.

## Receipt to record after owner actions

Record only non-secret facts in the release log: source commit, AAB SHA256, version/code, upload certificate fingerprint, live policy URL/check date, internal/closed release status and track name, actual opt-in URL, review result, aggregate qualifying tester count/period, and feedback summary. Keep personal tester addresses, Google credentials, service-account JSON and release keys outside Git and public evidence. If an action fails, record its exact error and the next concrete owner step; do not mark a draft as shipped.
